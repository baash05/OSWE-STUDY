Getting Started

1. OSWE Review Workflow

Scope

  • quick review methodology for source code auditing
  • methodology rather than a vulnerability list: identify the framework, trace input to a real sink, then validate impact

1.1. Start with the framework

  • identify the language and framework first
  • ASP.NET Core, Spring Boot, Laravel, Django, Flask, Express, Node, WordPress, raw PHP, Java Servlet, etc.
  • each framework has default patterns: routing, sessions, auth, models, templates, config
  • if you do not know the stack, you do not know the likely sink

1.2. Identify the route and request flow

  • find the controller / handler / route / page / servlet / view / endpoint
  • map: request → input → business logic → sink → response
  • look for GET, POST, PUT, DELETE, PATCH, route, @RequestMapping, app.get, router, controller, page model
  • note which data is attacker-controlled: query, form, cookies, headers, JSON, file upload

1.3. Identify the sink

  • shell / process execution
  • SQL execution
  • file read / file write / upload
  • template render
  • object binding / deserialization
  • session / auth / JWT / cookies
  • SSRF / HTTP client usage
  • file include / local include
  • custom logic around price, role, privilege, state change

1.4. Trace the input backward

  • start at the sink
  • work backward to where the value came from
  • ask: is this from query string, POST body, JSON, cookie, file, header, env, config, database?
  • if it is attacker-controlled and reaches a sink, test it

1.5. Check the framework defaults

  • auth middleware
  • route ordering
  • generic vs specific routes
  • session setup
  • model binding and validation
  • file upload handling
  • template rendering with raw output
  • config and environment handling

1.6. Look for dangerous wrappers

  • exec, system, Process.Start, Runtime.exec
  • require, include, readFile, open, File.ReadAllText
  • unserialize, readObject, ObjectInputStream, BinaryFormatter
  • render, @Html.Raw, th:utext, {{ ... }}, ${...}
  • raw SQL, query, execute, FromSqlRaw, DbContext, JDBC
  • HttpClient, requests, curl, fetch, WebClient

1.7. Check the “safe” code for bypasses

  • trim(), replace(), lower(), strip_tags(), regex, normalization
  • these are only useful if they gate a real sink
  • most of the time they are rabbit holes unless they directly affect raw SQL / shell / file access / template output

1.8. Look for auth and privilege issues

  • missing auth checks
  • auth check on only one route or one method
  • privilege in request body or object
  • secret in config or JS
  • IDOR on object IDs, user IDs, roles, file names
  • access control in middleware, filters, or custom guards

1.9. Look for object mutation / binding

  • req.body, Request.Form, @RequestBody, ModelBinding, BeanUtils.copyProperties, Object.assign, extract, new User(...)
  • user-controlled keys mutating roles, config, permissions, admin flags, default values

1.10. Look for upload + execution chains

  • upload file to webroot or app dir
  • later included, rendered, or executed
  • web shell, theme file, plugin file, template file, config file
  • check whether file path is user-controlled and later used in a sink

1.11. Look for SSRF / internal service access

  • outbound HTTP from request input
  • URL built from user input
  • no localhost / internal IP block
  • metadata service access or internal admin endpoints reachable

1.12. Check business logic paths

  • price manipulation
  • discount logic on backend not frontend
  • password reset flow
  • token reuse
  • multi-step workflows with missing state validation
  • role assignment or admin creation flows
  • state change abuse: approve / refund / transfer / cancel / redeem

1.13. Check for second-order flows

  • trace input stored in a database, session, cache, file, queue, or log before it reaches a sink
  • inspect later requests, background jobs, admin views, exports, and scheduled tasks that consume stored data
  • do not require the source and sink to occur in the same request

1.14. Check reachability conditions

  • record the required role, route state, feature flag, tenant, object owner, or prior workflow step
  • distinguish a dangerous sink from a sink the attacker can actually reach
  • check alternate routes, HTTP methods, error paths, and unauthenticated entry points

1.15. Mark trust-boundary crossings

  • note transitions such as request → database → worker, request → session, or upload → scheduled task
  • check whether validation, encoding, or authorization assumptions change at each boundary
  • follow data through queues, files, caches, and internal service calls

1.16. Inspect errors and fallback paths

  • review exception handlers, default values, alternate branches, and failed validation behavior
  • check whether security checks are skipped when parsing, lookup, or authorization fails
  • compare normal and error responses for useful disclosure or changed control flow

1.17. Chain the impact

  • after finding a primitive, ask what it enables next: disclosure, credential recovery, privilege escalation, file write, or code execution
  • trace available credentials, internal services, writable paths, and privileged processes
  • prefer the shortest demonstrable chain to meaningful impact

1.18. Then use payloads

  • only after sink + input flow are clear
  • use payloads to confirm exploitability
  • not to begin the review

1.19. Review order

1. framework 2. route 3. auth / middleware 4. input source 5. sink 6. input flow 7. payload validation 8. impact assessment

1.20. Final rule

  • if you cannot explain the data flow from input to sink, you do not have a bug yet
  • a bug is only real if you can show attacker input reaches a dangerous sink and impacts security

1.21. High-value questions

  • What is the entry point?
  • What is the sink?
  • What is the user-controlled data?
  • Is there a bypass in routing, auth, or validation?
  • Is the file/upload/SQL/object/HTTP call raw and attacker-controlled?
  • Can the impact be code execution, data exposure, auth bypass, or state change?

2. VS Code Network Debugging

Scope

  • remote file access, debugger attachment, port forwarding, path mapping, troubleshooting, and cleanup for authorized application testing

2.1. Prepare the Remote Host

  • Confirm the application runs remotely: SSH in and run its normal start command, then check its health URL or expected output.
  • Confirm the debugger and runtime are installed remotely: run commands such as python --version, java -version, dotnet --info, and the language debugger's version command.
  • Record the remote host, SSH port, application port, and debug port.
  • Use an authorized host and protect debugger ports with authentication or a firewall.

2.2. Connect VS Code to the Remote Files

  • Install the Remote - SSH extension.
  • Open the Command Palette and run Remote-SSH: Connect to Host.
  • Open the project folder through the remote VS Code window.
  • Install language extensions in the remote environment when prompted.

2.3. Configure the Debugger

  • Create or edit .vscode/launch.json on the remote workspace.
  • Use request: "launch" to start the program remotely.
  • Use request: "attach" when the program is already running.
  • Set remote paths, working directory, environment variables, and runtime arguments.
  • Add source-file mappings when local and remote paths differ.

2.4. Forward Network Ports

  • Forward the application port so VS Code or a browser can reach the remote service.
  • Forward the debugger port when attaching over TCP.
  • Prefer SSH port forwarding over exposing debugger ports publicly.
  • Confirm the forwarded port works: open the forwarded URL or run curl http://127.0.0.1:<local-port>.
  • Check for local port conflicts with lsof -nP -iTCP:<local-port> -sTCP:LISTEN.

2.5. Troubleshoot Connection Problems

  • Check SSH connectivity and the remote VS Code server status.
  • Confirm the process is listening: run ss -ltnp | grep <port> on Linux or lsof -nP -iTCP:<port> -sTCP:LISTEN on macOS.
  • Check remote firewall rules and SSH forwarding settings.
  • Verify interpreter, SDK, dependencies, permissions, and environment variables are remote.
  • Recheck path mappings when breakpoints show as unverified.

2.7. Clean Up

  • Stop the debug session and terminate temporary processes.
  • Remove temporary port forwards and debug listeners.

Decompile

3. Java Decompilation

3.1. Identify the Artifact

  • Find .jar, .war, .ear, .class, or Android .apk files.
  • Record the Java version and application framework if visible.
  • Preserve the original file and work on a copy.

3.2. Extract the Archive

  • .jar / .war / .ear: unzip into a separate directory.
  • Inspect WEB-INF/classes, WEB-INF/lib, and META-INF.
  • List embedded libraries and configuration files.

3.3. Decompile the Classes

  • Use a Java decompiler such as CFR, FernFlower, or JADX.
  • Example: java -jar cfr.jar app.jar --outputdir decompiled
  • Decompile individual .class files when the full archive is noisy.
  • Expect approximate source, not the original source code.

3.4. Search the Output

  • Search routes, controllers, filters, servlets, and security configuration.
  • Search sensitive sinks: Runtime.exec, ProcessBuilder, JDBC queries, file APIs, deserialization, reflection, and template rendering.
  • Trace request parameters, headers, cookies, and uploaded files to those sinks.
  • Check configuration for secrets, debug mode, internal URLs, and dangerous options.

3.5. Confirm Behavior

  • Compare decompiled logic with bytecode tools such as javap -c -p.
  • Verify important findings by reproducing the request in a local or authorized lab.
  • Check library versions and compare them with known vulnerabilities.

3.6. Common Limitations

  • Variable names, comments, formatting, and some generic types may be lost.
  • Obfuscation can hide class and method meanings.
  • Decompiled control flow may be inaccurate around synthetic or optimized bytecode.
  • Treat decompiled code as a guide and validate high-impact conclusions against bytecode or runtime behavior.

4. .NET Decompilation

4.1. Identify the Artifact

  • Find .dll, .exe, .deps.json, .runtimeconfig.json, .cshtml, or published application files.
  • Identify the target runtime: .NET Framework, .NET Core, or modern .NET.
  • Preserve the original files and work on a copy.

4.2. Inspect the Application

  • Check web.config, appsettings.json, environment files, and launch settings.
  • Inspect bin, publish, wwwroot, and referenced assemblies.
  • Record framework and package versions from .deps.json or project metadata.

4.3. Decompile the Assemblies

  • Use ILSpy, ilspycmd, dnSpyEx, or dotPeek.
  • Example: ilspycmd -p -o decompiled app.dll
  • Open referenced DLLs when important logic is outside the main assembly.
  • Expect reconstructed C# rather than the original source code.

4.4. Common Decompiler Tools

  • ILSpy: green insect / bug icon; open-source .NET assembly browser.
  • ilspycmd: terminal icon; command-line ILSpy for scripted exports.
  • dnSpyEx: purple debugger-style icon; inspect, edit, and debug assemblies.
  • dotPeek: purple JetBrains logo; decompile and browse .NET assemblies.
  • ildasm: terminal or command-prompt icon; Microsoft IL disassembler.

4.5. Search the Output

  • Search controllers, Razor Pages, middleware, filters, minimal API routes, and authorization checks.
  • Search sensitive sinks: Process.Start, ProcessStartInfo, Assembly.Load, reflection, file APIs, SQL APIs, deserialization, and template rendering.
  • Trace query, form, JSON, header, cookie, and uploaded-file input to those sinks.
  • Check configuration for secrets, connection strings, debug settings, internal URLs, and unsafe options.

4.6. Confirm Behavior

  • Inspect IL with ILSpy or ildasm when reconstructed C# is unclear.
  • Compare method signatures and control flow across referenced assemblies.
  • Reproduce important findings only in an authorized local or lab environment.
  • Check package versions against known vulnerabilities.

4.7. Common Limitations

  • Comments, formatting, local names, and some source structure may be lost.
  • Obfuscation can hide types, methods, and control flow.
  • Compiler-generated async, iterator, and state-machine code can look unfamiliar.
  • Treat decompiled C# as a guide and validate high-impact conclusions against IL or runtime behavior.

Languages

5. PHP

Scope

  • PHP web-app review across raw PHP, Laravel, Symfony, WordPress, and CodeIgniter, with emphasis on framework behavior and dangerous sinks

5.0. Final rule

  • identify the framework first
  • identify the template engine second
  • then identify the real sink
  • only after that do you chase input flows and payloads

5.1. The 10 Patterns to Check First

  • User input and route confusion: $_GET, $_POST, $_REQUEST, $_COOKIE, $_SERVER, $_FILES, route files, router configs
  • Code execution: eval, assert, preg_replace(... /e ), create_function, call_user_func, call_user_func_array, array_map with string callable
  • Command injection: exec, shell_exec, system, passthru, popen, proc_open, pcntl_exec, curl | bash
  • Insecure deserialization / XXE: unserialize, serialize, yaml_parse, xml_parse, simplexml_load_string, DOMDocument::loadXML
  • SSTI: {{ ... }}, {% ... %}, <?= $var ?>, Blade, Twig, Smarty, render
  • XSS: echo, print, header, print_r, raw HTML output
  • File upload / write abuse: move_uploaded_file, file_put_contents, fopen, fwrite, rename, tmp_name, $_FILES
  • SQLi: mysqli_query, PDO::query, SELECT, ORDER BY, UNION, LIMIT
  • Traversal / file read abuse: file_get_contents, fopen, readfile, include, require, glob, opendir, file_exists, unlink
  • Mass assignment / object mutation: extract, parse_str, foreach ($_GET as ...), $_REQUEST, array_merge, array_walk, ->set, Session / config arrays

5.2. Identify the Stack

  • Plain PHP: $_GET, $_POST, $_REQUEST, $_COOKIE, $_SERVER, $_FILES, header(), echo, print, include, require
  • Laravel: Route::get, Route::post, Request, Input::get, request(), Response, View::make, Blade
  • Symfony: Controller, Request, ParameterBag, Response, Twig, render()
  • WordPress: add_action, add_filter, wp_remote_get, get_option, wpdb->get_results, query_posts, do_shortcode
  • CodeIgniter: ->get, ->post, input->get, view, model
  • Raw PHP file execution: include, require, include_once, require_once, eval, assert, preg_replace('/.../e')

5.3. Identify the Template Engine

  • Twig: {{ ... }}, {% ... %}
  • Blade: {{ ... }}, @php, @include, @foreach, @if
  • Smarty: {...}
  • Native PHP templates: <?= $var ?>, <?php echo $var ?>
  • Custom template loaders: render, template, view, mustache, handlebars
  • route → controller → template → user input

5.4. Routing

  • Plain PHP: index.php, mod_rewrite, .htaccess, custom routing, $_SERVER['REQUEST_URI'], parse_url, router
  • Laravel: Route::get, Route::post, Route::any, Route::resource, ->where, ->middleware
  • Symfony: @Route, @Method, router config, Request matching
  • WordPress: add_action('wp_ajax_...'), add_rewrite_rule, template_redirect, admin_post
  • Safe rule: specific before generic; generic before specific = danger
  • Search for: Route::, $_SERVER['REQUEST_URI'], router, rewrite, template_redirect, index.php?

5.5. Code Execution

  • eval($x), assert($x), preg_replace('/.*/e', ...), create_function(...), call_user_func($fn, ...)
  • shell_exec, exec, system, passthru, proc_open, popen
  • include $tainted, require $tainted, include_once, require_once
  • dynamic class loading: new $class(), call_user_func([$obj, $method]), ReflectionClass, unserialize()
  • template engines used with untrusted input and rendering context
  • search for: eval, assert, exec, system, include, require, preg_replace, call_user_func, new $
  • NOTE: The regex assert\( only works as a dynamic RCE string evaluator in PHP 7.x. In PHP 8.x, assert() was changed to a language construct; passing it a variable string containing code will throw a compiler error instead of executing it. Keep a red pencil note on the target's PHP environment version.

5.5.1. PHP RCE patterns

  • eval($_GET['cmd'])
  • assert($_POST['x'])
  • preg_replace('/.*/e', $_GET['p'], 'text')
  • include($_GET['file'])
  • require($userInput . '/config.php')
  • call_user_func($_GET['func'], $_GET['arg'])
  • new $className() where $className is user-controlled

5.5.2. High-value sinks / file names

  • exec.php, shell.php, commands.php, utils.php, loader.php, render.php, template.php, config.php
  • cmd, command, exec, shell, script, path, file, include, require, template, eval, func, class
  • system, exec, popen, proc_open, preg_replace, call_user_func, assert, include

5.5.3. What to do when you find it

  • Confirm user input reaches the sink
  • Check whether the sink is direct code execution or a wrapper around a shell
  • Check whether input is concatenated into a command or loaded path
  • Determine privileges and impact: file read, RCE, persistence, pivoting

5.6. Command Injection

  • system($cmd), exec($cmd), shell_exec($cmd), passthru($cmd), proc_open($cmd), popen($cmd)
  • bash -c, sh -c, powershell -Command, cmd /c
  • user input into cmd, command, exec, script, path, filename, url, args
  • search for: exec(, shell_exec, system(, passthru(, popen(, proc_open(, bash -c, cmd /c

5.7. Insecure Deserialization

  • unserialize($data), serialize($obj), yaml_parse, simplexml_load_string, DOMDocument::loadXML
  • object injection via __wakeup, __destruct, __toString, __call, gadget chains
  • PHP object injection often relies on magic methods and unsafe unserialize of request data
  • search for: unserialize, yaml_parse, simplexml_load_string, DOMDocument, serialize, $_POST, $_GET

5.8. SSTI

  • Twig: {{ ... }}
  • Blade: {{ ... }}
  • Smarty: {...}
  • native PHP template output: <?= $var ?>, <?php echo $var ?>
  • route → controller → template → user input
  • payloads usually hit {{, {%, <?=, ${, ${{ depending on the engine

5.9. XSS

  • echo, print, print_r, raw HTML responses, template output without encoding
  • $_GET, $_POST, $_COOKIE, $_SERVER, route params, headers, JSON
  • htmlspecialchars, strip_tags are helpful only if used correctly; raw output is a warning sign
  • search for: echo, print, HTML, template, render, Response, raw, Blade, Twig, <?=

5.10. File Upload

  • $_FILES, move_uploaded_file, fopen, fwrite, file_put_contents, tmp_name, name, type, size
  • extension allowlist / blacklist bypass
  • path traversal via upload center and user-controlled filename
  • ../, %2e%2e, ..%2f, symlinked upload dirs
  • web shell patterns: .php, .phtml, .phar, .jsp, .js, .html, .aspx, .sh, .py
  • search for: $_FILES, move_uploaded_file, file_put_contents, tmp_name, upload, name, type

5.11. SQLi

  • mysqli_query, mysqli_multi_query, PDO::query, PDO::prepare, DB::select, wpdb->get_results, raw SQL strings
  • SELECT, WHERE, ORDER BY, LIMIT, UNION, --, OR 1=1, ' OR '1'='1
  • if user input reaches WHERE, ORDER BY, LIMIT, OFFSET, HAVING, inspect closely
  • search for: query(, prepare(, SELECT, ORDER BY, UNION, wpdb, PDO

5.12. Directory Traversal

  • file_get_contents, fopen, readfile, include, require, glob, opendir, is_file, unlink
  • ../, ..\, %2e%2e, %2f, ..%2f
  • file reads from uploads, templates, configs, logs, caches, temp files
  • realpath, basename, dirname are not enough unless paired with a proper root check
  • zip slip: ZipArchive, ZipArchive::extractTo, unzip wrappers
  • search for: file_get_contents, readfile, fopen, include, require, glob, ZipArchive

5.13. Mass Assignment / Object Mutation

  • extract($_GET), parse_str, $_REQUEST, array_merge($_GET, $_POST), foreach ($request as $k => $v)
  • session / config mutation: $_SESSION, $_COOKIE, extract, array_walk, setcookie, register_globals legacy patterns
  • user-controlled keys mutating admin, roles, config, defaults, auth status
  • search for: extract, parse_str, $_REQUEST, $_SESSION, array_merge, foreach, setcookie

5.14. Auth / Session

  • $_SESSION, session_start, setcookie, session_regenerate_id, password_hash, password_verify, password_needs_rehash
  • header('Location: ...'), Authorization, Bearer, X-API-Key, token, jwt, firebase/php-jwt
  • is_admin, is_authenticated, role, admin, permissions
  • search for: session_start, $_SESSION, setcookie, Authorization, jwt, role, admin

5.15. SSRF

  • file_get_contents($url), curl_exec, fsockopen, stream_context_create, HttpClient, Guzzle, wp_remote_get, Requests
  • allow_redirects, verify, timeout, proxy, base_uri, url built from user input
  • internal IP / localhost checks: 127.0.0.1, localhost, 10.0.0.0/8, 172.16/12, 192.168/16, 169.254.169.254
  • search for: curl, file_get_contents, HttpClient, Guzzle, wp_remote_get, localhost, url

5.16. XML / XXE

  • simplexml_load_string, simplexml_load_file, DOMDocument::loadXML, DOMDocument::loadHTML, XMLReader
  • <!DOCTYPE, ENTITY, SYSTEM, PUBLIC
  • search for: simplexml_load, DOMDocument, DOCTYPE, ENTITY, SYSTEM, PUBLIC

5.17. Mass Assignment / Object Hydration

  • new User($_POST), new Model($data), array_map, extract, binding of request arrays to objects
  • user-controlled arrays turned into model objects, DTOs, config arrays
  • search for: new User, new Model, extract, $_POST, Request, bind, hydrate

5.18. Rabbit Holes

  • trim(), strtolower(), str_replace(), substr(), explode(), strpos(), preg_match()
  • rand(), mt_rand(), uniqid(), password_hash(), hash(), md5()
  • realpath(), basename(), dirname(), parse_url()
  • these are usually not bugs by themselves; they matter only if they gate a real sink
  • if it never reaches a sink, move on

5.19. KPI’s / High-Value Files

  • index.php, config.php, bootstrap.php, app.php, routes.php, settings.php, wp-config.php
  • .env, env, $_ENV, getenv(), putenv(), ini_set, parse_ini_file, session.save_path
  • PDO, mysqli, wpdb, Symfony services, Laravel container, WordPress hooks
  • eval, assert, exec, include, require, file_get_contents, curl, unserialize
  • if config is imported and then used in a sink, it is usually high value

5.20. Quick Review Rule

  • Start with the sink: shell, eval, file write, template render, SQL, open, session/auth.
  • Trace the user input backward.
  • If the “fix” is only trim(), strtolower(), str_replace(), regex, or normalization, it is usually a rabbit hole unless it gates a real sink.
  • NOTE/CLUE: dynamic include + object injection + config + request arrays + runtime globals.

6. Java

Scope

  • Java web-app review with Spring-first coverage plus Servlet, JSP, Struts, Thymeleaf, persistence, and serialization patterns

6.0. The 10 Patterns to Check First

  • Route precedence and generic-vs-specific confusion: @GetMapping, @PostMapping, @RequestMapping, @Controller, web.xml, doGet, doPost, @PathVariable
  • Code execution / reflection abuse: Runtime.getRuntime().exec, ProcessBuilder, ScriptEngine, ELProcessor, OGNL, Class.forName, newInstance
  • Command injection: ProcessBuilder, Runtime.exec, bash -c, cmd /c, powershell -Command
  • Insecure deserialization: ObjectInputStream, readObject, Serializable, yaml.load, Jackson polymorphic deserialization
  • Template injection / SSTI: JSP EL, Thymeleaf, Freemarker, Velocity, Mustache
  • XSS: HttpServletResponse, PrintWriter, response.getWriter(), @ResponseBody, JSP raw output
  • File upload / write abuse: MultipartFile, FileOutputStream, Files.write, transferTo, saveAs
  • SQLi: Statement, JdbcTemplate.query, EntityManager.createQuery, SELECT, ORDER BY, UNION
  • Traversal / file read abuse: FileInputStream, Files.readString, Paths.get, ResourceLoader, getResource, ZipFile
  • Object mutation / property binding abuse: setProperty, BeanUtils.copyProperties, Reflection, Class.forName, MBeanServer, @RequestBody

6.1. Identify the Stack

  • Spring Boot: @SpringBootApplication, @RestController, @Controller, @GetMapping, @PostMapping, @RequestMapping
  • Spring MVC: @Controller, @RequestParam, @PathVariable, @RequestBody, Model, HttpServletRequest
  • Servlet/JSP: HttpServlet, doGet, doPost, request.getParameter, response.getWriter, JSP EL, ${...}
  • Struts: Action, ActionForm, struts.xml, OGNL
  • Thymeleaf: th:text, th:utext, @{...}, ${...}

7.19. The Missing .NET Edge Cases (The Final 5%)

7.19.1. Mass Assignment via [AsParameters] (Minimal APIs)

  • Mechanics: Modern .NET Minimal APIs rely heavily on [AsParameters] to map incoming HTTP query strings, route values, or form fields directly into a custom record type or data structure. If that target record maps directly to an underlying database entity or internal system configuration, an attacker can over-post parameters to alter unlisted properties.
  • High-Value Sinks: [AsParameters], HttpContext.Request.AsParameters mappings.
  • Search Grep: \[AsParameters\]

7.19.2. Mass Assignment via JSON Source Generators

  • Mechanics: High-performance or Native AOT (Ahead-of-Time) compilation pathways utilize [JsonSerializable] contexts for serialization. If a structural data type is registered this way, standard reflection-based filters or runtime security middleware might fail to intercept how deep properties are bound, opening subtle mutation routes during payload deserialization.
  • High-Value Sinks: [JsonSerializable], JsonSerializerContext, JsonSerializerOptions.TypeInfoResolver.
  • Search Grep: \[JsonSerializable

7.19.3. SSRF via GraphQL / HotChocolate Framework

  • Mechanics: Enterprise applications often replace basic HttpClient patterns with GraphQL engines. Look for @stream directives, schema stitching, or dynamic client endpoints where user input can manipulate downstream queries, prompting the host server to fetch unintended internal endpoints or cloud metadata layouts.
  • High-Value Sinks: HotChocolate, AddGraphQLServer, StitchSchema, @stream.
  • Search Grep: HotChocolate | AddGraphQLServer

7.19.4. XML External Entity (XXE) via Legacy DataContractSerializer

  • Mechanics: While default XmlReader instances are safe in modern .NET, standard System.Runtime.Serialization.DataContractSerializer processes can be coerced into evaluating external entities if they are passed a custom XmlDictionaryReader that explicitly enables relaxed security properties or insecure resolvers for backward compatibility.
  • High-Value Sinks: DataContractSerializer, XmlDictionaryReader.CreateTextReader, XmlDictionaryReader.CreateMtomReader.
  • Search Grep: DataContractSerializer | XmlDictionaryReader

7.19.5. Authorization Bypass via Route Constraint Confusion

  • Mechanics: .NET evaluates API routes very strictly (e.g., [HttpGet("admin/{id:int}")]). If your authentication or gateway middleware filters access by checking if the path raw string simply starts with /admin/, an attacker appending extra slashes, path traversal parameters, or taking advantage of encoding differences between a reverse proxy (like Nginx) and Kestrel can bypass global authorization logic while still hitting the target action.
  • High-Value Sinks: [Route], [HttpGet], UseAuthorization misplacements relative to custom endpoints.
  • Search Grep: Route\( | UseAuthorization

  • Best OSWE clue: dynamic import + monkey patch + object mutation + config + runtime globals.

Vectors

10. Business Logic / IDOR (Insecure Direct Object Reference)

Scope

  • business-logic and access-control flaws, including IDOR, privilege bypass, state transitions, object mutation, enumeration, and race conditions

10.0. The 10 Patterns to Check First

  • Object IDs in URL or JSON: id, userId, accountId, orderId, fileId, reportId
  • Role or privilege checks: admin, isAdmin, role, permission, canEdit, owner, author
  • Multi-step workflow abuse: create → approve → pay → cancel → refund → delete
  • State transition abuse: pending → approved → shipped → refunded → deleted
  • Hidden or debug endpoints: /admin, /debug, /internal, /test, /dev, ?debug=1
  • Missing authorization on action endpoints: update, delete, transfer, reset, export, download
  • Request-body state override: server-side auth, ownership, or status values
  • Enumeration and weak object matching: guessable IDs or sequential records
  • Missing business-rule validation: price, coupon, discount, limit, quota, permission
  • Client-side trust: JS, hidden fields, cookies, query params, request body

10.1. IDOR / Direct Object Reference

  • changing id or userId to access another record
  • GET /invoice?id=42 → GET /invoice?id=43
  • GET /profile?user=1 → GET /profile?user=2
  • DELETE /orders/123 without ownership or admin check
  • GET /download?file=report.pdf with no path or ownership enforcement
  • often seen in APIs, dashboards, upload/download endpoints, admin functions

10.2. Auth / Privilege Bypass

  • route protected only on one path or one controller method
  • auth check in middleware but not on a sub-route or action
  • privileged flag in body: {"admin": true} or {"role": "admin"}
  • user can create own session or token with stronger role
  • hidden flag in cookie or query string controlling access
  • insecure default permissions or lower-role fallback

10.3. Money / Price / Discount Abuse

  • discount or coupon validated only client-side
  • price changed in request body before payment/checkout
  • negative amounts, duplicate coupon use, refund abuse, bypass of max limit
  • free order by modifying total / tax / quantity / currency
  • state transition: pending → paid without proper validation

10.4. Password / Reset / MFA Abuse

  • reset token not bound to user
  • token replay after use or after logout
  • password reset flow with predictable token or no verification
  • bypass via user-supplied email or id in reset link
  • weak 2FA or missing session re-check on permission changes

10.5. Multi-Step Workflow Abuse

  • create record → change status → bypass rules
  • approve without required second factor
  • export before validation
  • delete object without checking parent object or owner
  • cancel order after refund or transfer has already happened
  • check state transitions: pending → approved → completed → archived

10.6. State Validation Bugs

  • missing check for current state before action
  • user can do action when object is in wrong state
  • action allowed for one role but not enforced on backend
  • isActive, ownerId, approved, locked, deleted, admin, enabled changed from request input

10.7. Mass Assignment / Object Mutation

  • user can set fields like role, admin, is_active, owner, verified, balance, permissions
  • JSON payload maps directly into user model or database row
  • custom DTO / body binding with too many allowed fields
  • request body or query data controlling backend state without validation

10.8. Hidden / Debug / Internal Routes

  • /admin, /debug, /internal, /metrics, /health, /test, /setup
  • debug features left behind in production
  • endpoints protected by user-agent or hidden parameter checks
  • feature flags exposed or toggled by request parameter

10.9. Client-Side Trust Bugs

  • JS validation only
  • hidden input fields set to privileged values
  • request body fields for price, amount, status, role, user_id
  • cookie or local token used as access-control signal
  • app trusts the client’s state more than the server’s canonical state

10.10. Enumeration / Guessable IDs

  • predictable IDs: 1,2,3,4
  • sequential numeric records
  • IDs leaked in page source, API responses, logs, hidden fields, JS bundles
  • access without authorization or ownership check
  • admin or account objects reachable with guessed IDs

10.11. File Access / Download Abuse

  • download?id=123 returns another user’s document
  • report=123 exposes arbitrary file or attachment
  • file names or object IDs used without ownership check
  • exported/report endpoints leak data without authorization

10.12. Search / Filter Abuse

  • filter values allow access to records outside intended scope
  • ?user_id=123 or ?account=999 can cross boundaries
  • search results include unauthorized objects if filters are not enforced server-side
  • backend trust of query params instead of session / auth object

10.13. Race / Time-of-Check Time-of-Use

  • two requests can alter state between read and write
  • apply coupon twice
  • redeem gift card twice
  • delete while another operation is reading it
  • approve and refund in same workflow without lock or validation

10.14. High-Value Search Terms

  • id, userId, ownerId, accountId, invoiceId, orderId, fileId, role, admin, permission, owner, isAdmin, canEdit, approved, status, balance, price, discount, coupon, export, download, reset, token

10.15. Quick Review Rule

  • if a user can influence a record ID, role, status, amount, or action, inspect it
  • check server-side ownership and privilege checks
  • check step-by-step flow validation
  • if the action has a real-world consequence, it is high value

10.16. Quick Payloads

IDOR

  • change id=1 to id=2
  • change userId=abc to userId=admin
  • manipulate orderId, invoiceId, fileId, reportId
  • tamper with query param, JSON body, hidden form field

Privilege Abuse

  • {"role":"admin"}
  • {"admin":true}
  • ?isAdmin=true
  • ?role=admin
  • cookie or token value that bypasses role check

State Abuse

  • approve without required checks
  • refund after cancel
  • apply coupon twice
  • negative price or free purchase
  • bypass quantity / limit / coupon validation

10.17. Final Rule

  • business logic bugs are often easier to exploit than classic injection
  • they usually come from missing server-side checks, not missing payloads
  • if the app trusts client-controlled state, inspect it aggressively

11. Information Disclosure

Goal

  • Find places where the app leaks data that should not be visible.
  • Confirm the leak is real, useful, and reachable.
  • Use it to pivot to auth bypass, config access, secrets, internal hosts, source code, logic, or admin functions.
  • In OSWE, disclosure is usually a stepping stone, not the final issue.

11.1. How to Discover It

A. Error and exception handling

  • 500 errors, stack traces, debug pages, tracebacks, verbose errors.
  • Application crash output with file paths, framework names, library versions.
  • SQL errors revealing query structure, table names, columns.
  • Deserialization errors exposing class names and internal object graphs.
  • Unhandled exceptions in API endpoints, file upload handlers, template rendering, session logic.

B. Response headers

  • Server, X-Powered-By, X-AspNet-Version, Stack, Framework, Tool.
  • Set-Cookie with insecure flags or session structure.
  • Location leaks internal paths or redirect chains.
  • Content-Type with unexpected mime confusion.
  • Via, X-Forwarded-*, X-Backend-*, X-Envoy-*, X-Cache.

C. URLs and directory structure

  • /admin, /debug, /manage, /metrics, /actuator, /phpinfo.php, /console, /logs.
  • Backup names: .bak, .old, .orig, .save, .tmp, .zip, .sql, .tar.gz.
  • Source files: .git, .svn, .hg, .env, config, settings, secrets, swagger, openapi.
  • Default framework endpoints, health pages, debug routes.
  • Unprotected API docs and schema files.

D. Source and config exposure

  • /.git/config, /.git/HEAD, /.svn, /.hg.
  • config.php, settings.py, application.properties, appsettings.json, web.config.
  • .env, .env.local, .env.production, docker-compose.yml, kubernetes manifests.
  • Hardcoded secrets, tokens, DB URLs, API keys, encryption keys.
  • Debug configs and feature flags.

E. File read / directory traversal

  • Read arbitrary files via ../, %2e%2e, encoded traversal.
  • Access logs, configs, backups, password stores, certificate keys.
  • Exposed upload directories or static file roots.
  • ZIP extraction leads to local file disclosure.

F. IDOR and object enumeration

  • IDOR = insecure direct object reference: user-controlled object identifiers are accepted without proper authorization checks.
  • User IDs, ticket IDs, invoice IDs leaking internal records.
  • Enumerating GET /account/1, .../2, .../3.
  • Hidden API endpoints returning other users’ objects.
  • Access control checks performed only on some routes.

G. Verbose auth / session behavior

  • Distinct error messages for bad username vs bad password.
  • Account enumeration via response timing, status codes, JS messages, HTML differences.
  • Session token leakage in URLs, logs, Referer, JS, cached responses.
  • JWT structure leaks roles, algorithms, issuer, claims.

H. Caching and browser behavior

  • Cache-Control, Pragma, Expires, ETag on sensitive pages.
  • Shared caches, CDN, proxies storing secret responses.
  • Private data in HTML comments, JS constants, JSON blobs, API responses.
  • Browser devtools, saved pages, search indexes, logs.

I. Verbose backend / framework behavior

  • Flask/Django/FastAPI debug mode pages.
  • Java/Spring boot actuator endpoints.
  • .NET environment info, route maps, exception dumps.
  • phpinfo(), server status, status.jsp, health endpoints.
  • GraphQL introspection and schema dumping.

J. Common OSWE-style leakage patterns

  • Default app pages leak internal stack layout.
  • Error pages include file names and line numbers.
  • print() or logging of raw request data.
  • Debug mode left on in prod.
  • Input reflected into templates or errors without encoding.
  • Secrets in commit history, backups, or packaged static assets.

11.2. What to Do With It

A. Verify the disclosure is real

  • Reproduce the leak with a single crafted request.
  • Confirm it is not a front-end-only artifact or stale cache.
  • Check whether data is static or dynamically generated.
  • Determine exact scope: one user, all users, internal system, admin-only, all hosts.

B. Classify the value

  • High value: credentials, session tokens, API keys, secrets, internal IPs, DB URIs, admin paths.
  • Medium value: stack traces, source file names, framework versions, route names, config fragments.
  • Low value: harmless metadata, generic headers, minor version numbers.

C. Pivot from the leak

  • Secrets -> auth bypass / API abuse.
  • Internal hostnames -> SSRF / port scanning / service discovery.
  • Config values -> DB access, service credentials, JWT signing key.
  • Stack traces -> code path identification and deeper exploitation.
  • Source file names -> target likely vulnerable functions and business logic.
  • Admin endpoints -> privilege escalation and direct takeover.

D. Use it for chain building

- auth bypass - IDOR - SSRF - SQL injection via DB creds or error details - remote command execution via misconfigured secrets - token forgery and privilege escalation - file read/write via path or upload config

  • Disclosure often leads to:

E. Make it exam-usable

  • Capture exact endpoint, request, response, and leak type.
  • Reflect whether leak is direct, reflected, or reachable via unprotected route.
  • Map what object is exposed and what security boundary it breaks.
  • Note whether the leak helps identify deeper vulnerabilities.

F. Operational discipline

  • Keep the finding narrow, reproducible, and tied to a security boundary.
  • Do not confuse “leak of metadata” with “vulnerability” unless it leads to impact.
  • In OSWE, the key question is: what does this leak enable?
  • If it exposes no actionable boundary break, treat it as a lower-priority observation.

11.3. High-Value Discovery Checklist

  • 500 + traceback + file path + framework banner
  • /admin, /debug, /actuator, /env, /swagger, /graphql
  • .env, settings, config, web.config, application.properties
  • Authorization, jwt, cookies, tokens, bearer secrets
  • internal IPs, hosts, DB URIs, private URLs
  • SQL/ORM errors, stack dumps, object introspection
  • hidden backups, archives, and source-control metadata
  • debug mode enabled, verbose logging in production

11.4. Core Mental Model

  • Information disclosure is not just “data was exposed”; it is “a trust boundary failed.”
  • The real question is: what did the app reveal that should have stayed internal?
  • In an exam, the best disclosure findings are the ones that immediately support the next exploitation step.

12. Local File Inclusion (LFI) / File Upload + Execution

Scope

  • local file inclusion and file-based execution paths, including uploads, web shells, traversal, and chained file sinks

12.0. The 10 Patterns to Check First

  • Direct File Inclusion: include, require, include_once, require_once
  • File Read / LFI: file_get_contents, readfile, fopen, fopen(..., 'r'), file()
  • Input to Include Paths: $_GET, $_POST, $_REQUEST, $_COOKIE, $_SERVER, path, file, page, template, lang, module
  • File Upload Sinks: move_uploaded_file, $_FILES, tmp_name, name, type, content, upload
  • File Write / Web Shell Creation: file_put_contents, fopen(..., 'w'), fwrite, rename, copy, rename, mv
  • Execution After Upload or File Inclusion: exec, system, shell_exec, passthru, proc_open, popen, Runtime.exec, Process.Start
  • Traversal / Path Bypass: ../, ..\, %2e%2e, %2f, ..%2f
  • File Enumeration and Disclosure: glob, opendir, readdir, scandir
  • Archive Abuse / RCE: ZipArchive, tar, extract, unzip, upload / decompression
  • Common LFI Abuse Vectors: template, view, render, include, layout, theme, locale, language

12.1. LFI Basics

  • file include from user-controlled path: include($_GET['page'])
  • file read from user path: readfile($_REQUEST['file'])
  • ../, ..\, ..%2f, %2e%2e%2f are the normal bypasses
  • often combined with ?page=../../etc/passwd or ?file=../../config.php
  • include path may be relative to app root or a webroot subdirectory
  • sometimes the app blocks ../, but encoded traversal still succeeds

12.2. Common Include Sinks

  • PHP: include, require, include_once, require_once, file_get_contents, fopen, readfile
  • Node: fs.readFile, fs.readFileSync, path.join, require, import(), res.sendFile, readFileSync
  • Java / Spring: new FileInputStream, Paths.get, ClassPathResource, ResourceLoader, readAllBytes
  • .NET: File.ReadAllText, File.OpenRead, Path.Combine, PhysicalFileProvider, IWebHostEnvironment
  • If user input feeds the file path, inspect immediately

12.3. High-Value File Targets

  • /etc/passwd
  • /etc/shadow
  • /etc/hosts
  • /etc/apache2/sites-enabled/*
  • /etc/nginx/*
  • C:\Windows\win.ini
  • C:\Windows\System32\drivers\etc\hosts
  • config.php, settings.php, database.php, .env
  • wp-config.php, application.properties, application.yml, web.config, appsettings.json
  • uploads/, tmp/, cache/, logs/, sessions/

12.4. File Upload Abuse

  • upload endpoints accept file, upload, attachment, import, avatar, image, document
  • $_FILES, Request.Form.Files, MultipartFile, req.files, multer, FileStream, transferTo
  • file names: filename, name, tmp_name, originalname, path, upload_dir
  • extension abuse: .php, .phtml, .jsp, .aspx, .html, .js, .svg, .xml, .jspx, .war, .sh, .py
  • content-type abuse: image/png, text/html, application/x-php, text/plain, application/octet-stream
  • path traversal via ../, encoded traversal, or upload dir + user-chosen filename

12.5. Upload + Execution Chains

  • upload file → store under web root → access via browser → execute code
  • upload file → later included by app → code executes from plugin/theme/config path
  • upload file → later processed by app as template / script / config file
  • upload file → shell or script is run by backend functions or cron job later
  • common chain: upload -> save -> include/execute -> code execution

12.6. Very Common Upload + Execution Patterns

  • PHP: move_uploaded_file($_FILES['file']['tmp_name'], $target) then include($target) or file_get_contents($target)
  • PHP: file_put_contents($uploadDir . $_FILES['file']['name'], $data) then browser hits the file
  • Node: fs.writeFile / writeFileSync to web root, then request serves the file or it is imported / executed later
  • Java: FileOutputStream / transferTo to upload dir, then file is served or run as JSP / JSPX / WAR / script
  • .NET: File.WriteAllBytes, Request.Form.Files, then file is served / interpreted / loaded by app

12.7. Execution Sinks After Upload

  • PHP: exec, system, shell_exec, passthru, popen, proc_open, include, require, assert, eval
  • Node: child_process.exec, spawn, fork, vm, Function, require, import()
  • Java: Runtime.exec, ProcessBuilder, ScriptEngine, Class.forName, ELProcessor
  • .NET: Process.Start, Assembly.Load, Activator.CreateInstance, MethodInfo.Invoke
  • If uploaded content can be executed or included, treat it as a direct RCE vector

12.8. Web Shell Patterns

  • web shell only matters if it is reachable and the app will execute or serve it

12.9. File Inclusion + Upload Combos

  • upload script writes file under web root and include/require later reads it
  • upload script writes to config directory and app loads it on next request
  • plugin/theme upload uses included code path; uploaded package runs after activation
  • template or language file upload is later rendered or included as part of app localization or theming
  • archive upload extracts to a web-serving directory; extracted files are then invoked

12.10. Traversal / Bypass Patterns

  • ../../etc/passwd
  • ..\..\windows\win.ini
  • ../../../var/www/html/config.php
  • %2e%2e%2fetc/passwd
  • %2e%2e%5cwindows\win.ini
  • ..%2f..%2f..%2fetc/passwd
  • ..//..//..//etc/passwd
  • double-encoded traversal: %252e%252e%252f
  • path.normalize or basename by themselves are not real fixes without root enforcement

12.11. Useful Search Terms

  • include|require|readfile|file_get_contents|fopen|glob|opendir
  • move_uploaded_file|$_FILES|upload|tmp_name|originalname|multipart|transferTo
  • file_put_contents|fwrite|rename|copy|writeFile|writeFileSync
  • exec|system|shell_exec|passthru|proc_open|Process.Start|Runtime.exec
  • ..\/|%2e%2e|../|upload|web shell|shell.php

12.12. Quick Review Rule

  • Start with the file path the app opens or includes.
  • Then check whether user input reaches it.
  • Then check whether the file is writable by the app or uploadable by a user.
  • Then check whether the file is later executed, rendered, or included.
  • If file content is reachable from the web or code path, treat it as high value.

Traversal / LFI

  • LFI is often just the first step.

13. SQL Injection Cheat Sheet

Scope

  • SQL injection review and exploitation reference for union, error, blind, time-based, enumeration, and evasion techniques
  • Use after tracing input to a real SQL sink rather than as a replacement for source review.

13.1. SQLi Checklist

  • User input reaches SELECT, INSERT, UPDATE, DELETE, ORDER BY, LIMIT, OFFSET, HAVING, WHERE
  • Input is concatenated into SQL string or interpolated into raw query text
  • Query is built from request parameters, cookies, headers, body, file data, JSON, or server state
  • DB layer is raw SQL, ORM raw SQL, or string-built query builder
  • Authentication, search, filtering, sort, pagination, exports all matter

13.2. Basic Payloads

  • ' OR '1'='1
  • " OR "1"="1
  • admin' --
  • admin' #
  • ') OR 1=1 --
  • UNION SELECT NULL--
  • UNION SELECT NULL,NULL--
  • ORDER BY 1--
  • ORDER BY 1,2,3--
  • LIMIT 1,1--
  • OFFSET 1--
  • OR 1=1--
  • AND 1=1--
  • AND 1=2--

13.3. Common Injection Points

  • WHERE username = '$user'
  • WHERE id = $id
  • ORDER BY $sort
  • LIMIT $limit
  • OFFSET $offset
  • HAVING $filter
  • SELECT ... FROM ... WHERE ...
  • dynamic SQL in DAO / repository / mapper code
  • Raw query builders: raw(), execute(), query(), SELECT, FROM, WHERE

13.4. Comment Syntax by DB

  • MySQL / MariaDB: -- , #, /* */
  • PostgreSQL: -- , /* */
  • MSSQL: -- , /* */
  • Oracle: -- , /* */
  • SQLite: -- , /* */
  • If one form fails, try another comment style or inline syntax variant

13.5. Union-Based SQLi

  • UNION SELECT NULL--
  • UNION SELECT NULL,NULL--
  • UNION SELECT 1,2,3--
  • UNION ALL SELECT 1,2,3--
  • UNION SELECT username,password FROM users--
  • UNION SELECT version(),database(),user()--
  • Use ORDER BY to find the right column count
  • Need output reflected in the response to be useful

13.6. Error-Based SQLi

  • ' OR 1=1--
  • OR 1=cast(database() as int)--
  • AND 1=(SELECT 1 FROM dual)-- (DB-specific)
  • UNION SELECT @@version--
  • UNION SELECT USER()--
  • UNION SELECT current_database()--
  • Useful when the application echoes SQL errors or DB exceptions

13.7. Blind SQLi

  • AND 1=1--
  • AND 1=2--
  • AND SUBSTRING((SELECT version()),1,1)= '5'--
  • AND ASCII(SUBSTRING((SELECT database()),1,1))>64--
  • AND (SELECT COUNT(*) FROM users)>0--
  • OR 1=1--
  • Good for boolean conditions, time delays, and response differences

13.8. Time-Based SQLi

  • MySQL: AND SLEEP(5)--
  • PostgreSQL: AND pg_sleep(5)--
  • MSSQL: WAITFOR DELAY '0:0:05'--
  • Oracle: DBMS_LOCK.SLEEP(5)--
  • Use when there is no visible SQL output but the response timing changes

13.9. Boolean / Response-Based Checks

  • AND 1=1
  • AND 1=2
  • OR 1=1
  • ' OR '1'='1
  • ' OR 'x'='y
  • Differences in page content, errors, login success, or redirect behavior often reveal injection

13.10. Common DB Enumeration

  • MySQL: SELECT version(), database(), user()
  • PostgreSQL: SELECT version(), current_database(), current_user
  • MSSQL: SELECT @@version, DB_NAME(), SUSER_SNAME()
  • Oracle: SELECT banner FROM v$version
  • SELECT table_name FROM information_schema.tables--
  • SELECT column_name FROM information_schema.columns WHERE table_name='users'--
  • SELECT username,password FROM users--

13.11. DB-Specific

  • MySQL: information_schema, users, mysql.user, @@version, database(), sleep()
  • PostgreSQL: information_schema, pg_catalog, current_database(), current_user, pg_sleep()
  • MSSQL: sys.objects, sys.columns, INFORMATION_SCHEMA, @@version, WAITFOR DELAY
  • Oracle: ALL_TABLES, ALL_TAB_COLUMNS, v$version, DBMS_LOCK.SLEEP
  • SQLite: sqlite_master, pragma_table_info, sqlite_version()

13.12. Filter Evasion

  • URL encoding: %27, %22, %23, %2d%2d
  • double encoding: %2527
  • whitespace tricks: newline, tab, carriage return, comments
  • /**/ instead of space
  • case changes: OR, or, Or
  • string truncation / aliasing / comments when the app normalizes input

13.13. SQLi in Different Query Shapes

  • login form: username / password
  • search: q, search, keyword, term
  • sort: sort, order, orderby, field, direction
  • pagination: page, limit, offset, start, rows
  • filter: category, status, id, user, role
  • if user input reaches a raw SQL string in any of these, test it

13.14. Typical High-Value Patterns

  • SELECT * FROM users WHERE username = '...';
  • SELECT * FROM products WHERE category = '...' ORDER BY ...
  • SELECT * FROM invoices WHERE id = ... LIMIT ...
  • INSERT INTO users (username,password) VALUES ('...')
  • UPDATE users SET password='...' WHERE id=...
  • DELETE FROM users WHERE id=...
  • If the app builds SQL dynamically, assume raw input may be dangerous until proven otherwise

13.15. Quick Review Rule

  • Start with the SQL sink, not with payloads.
  • Trace request data backward.
  • Check whether the query is parameterized / safe.
  • If raw SQL is present, test for boolean, union, time, or error-based injection.
  • If it never reaches a raw SQL sink, it is not SQLi.

13.16. Useful Search Terms

  • SELECT|INSERT|UPDATE|DELETE|ORDER BY|LIMIT|OFFSET|HAVING|UNION
  • query\(|execute\(|raw\(|prepare\(|statement|mysqli|PDO|sql
  • WHERE .*\$|WHERE .*request|filter|sort|page|offset|id
  • sqlalchemy|jdbc|preparedstatement|executeQuery|ExecuteReader

13.18. Final Rule

  • SQLi is usually not a random payload problem; it is a raw SQL construction problem.
  • If you find user input in a SQL string, test it.
  • If you find parameterized queries or safe ORMs, move on unless there is a raw path or custom SQL builder.
